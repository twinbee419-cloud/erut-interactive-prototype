# 결과 분석 내보내기·3D·DAQ 재검토

> Codex · 2026-11-11 · `43_MARK_Claude-반영.md` §3의 3항목. Notion `[C-PRJ-06] 결과 분석` 3문서, `[C-PRJ-03] 종합 결과`, `[C-RPT-02] 스캔 보고서`를 새로 읽고 로컬 저장 사양과 대조. §4 및 기존 미결 제외. 판정 없이 차이와 구현 질문만 기록.

**blocking 1 · should-fix 4 · nit 1**

## blocking

1. **Cloud에 올릴 파일의 데이터 계약이 없음.** ① 내보내기 용도는 Cloud 웹 직접 업로드인데, 파일 1개의 확장자·압축만 개발팀에 맡겼고 내부 구조, 필드 식별자·버전, Cloud 수신 측의 해석 계약은 명시되지 않음. ② Notion `[C-PRJ-06] 결과 분석-파형 영역` §검사 데이터 내보내기; `03_dev_handoff/Result_Analysis_Storage_Spec_v1.0.md:135-150`. ③ Sight의 파일 생성과 Cloud의 업로드·결과 재현을 독립 구현하면 동일 데이터를 서로 다르게 읽을 수 있어 종단 기능에 착수할 기준이 부족함. ④ **개발 확인 질문:** 파일 스키마·버전·검증 방식과 Cloud 업로드 수신 계약을 어느 팀이 정하고, 양쪽이 어떤 사양을 공유하는가?

## should-fix

2. **마킹 일부 제외 후 내보내기 진행 조건이 비어 있음.** ① 공통 `[저장]`은 이미 시작된 마킹의 삭제·사유 수정만 제외하고 나머지를 저장하며, 제외 번호 팝업을 띄움. 내보내기는 “저장 성공 시 이어서”라고만 해 이 팝업 확인 전후 어느 때 파일을 만들지, 제외된 내용을 사용자에게 보여준 뒤에도 자동 진행할지 불명확함. ② Notion `[C-PRJ-06] 결과 분석-사이드바(교정)` §저장·초기화·삭제, `-사이드바(마킹)` §저장, `-파형 영역` §검사 데이터 내보내기; `Result_Analysis_Storage_Spec_v1.0.md:124-129,148,161-163`. ③ 저장은 성공해도 사용자가 요청한 변경 중 일부는 파일에 들어가지 않음. ④ **확인 질문:** 제외 건이 발생하면 번호 팝업을 확인한 뒤 자동으로 내보낼지, 사용자가 계속 여부를 다시 결정할지?

3. **내보내기 중 마킹 상태의 기준 시점이 없음.** ① 파일에는 “내보내는 시점”의 `status`를 넣지만, 자동화 장비 제어 페이지는 내보내기 진행 중에도 `status`·`failReason`을 갱신할 수 있음. 어느 시점의 일관된 스냅샷을 채택하는지 명시되지 않음. ② Notion `[C-PRJ-06] 결과 분석-파형 영역` §검사 데이터 내보내기, `-사이드바(마킹)` §상태; `Result_Analysis_Storage_Spec_v1.0.md:126-129,145,148-149,163`. ③ 긴 파일 생성 중 상태가 바뀌면 파일 안의 목록과 화면 알림이 서로 다른 시점을 가리킬 수 있음. ④ **개발 확인 질문:** 저장 완료 후 파일 생성을 시작할 때 마킹 전 필드를 한 번에 고정하는가, 다른 기준 시점을 쓰는가? 진행 중 도착한 상태 알림은 화면에 언제 반영하는가?

4. **내보내기 진행 중 문서 탭 이동 범위가 불명확함.** ① 내보내기 절은 “화면 dimmed + 조작 불가”이나 공통 문서 탭까지 막는지 적지 않음. 기존 규칙은 다른 문서 탭 이동을 허용하고 결과 분석 탭을 닫을 때만 미저장 팝업을 사용함. ② Notion `[C-PRJ-06] 결과 분석-파형 영역` §검사 데이터 내보내기, `-사이드바(교정)` §저장하지 않은 변경. ③ 이동·닫기가 가능하면 완료 토스트·실패 팝업을 어느 탭에 보여줄지, 진행 작업을 유지할지 정해야 함. ④ **확인 질문:** 진행 중 공통 문서 탭 전환·결과 분석 탭 닫기를 차단하는가? 허용한다면 작업과 완료·실패 알림의 귀속은 무엇인가?

5. **헤더의 이전 명칭이 남음.** ① 같은 파형 문서의 §레이아웃은 헤더 우측을 “표시 옵션·대상 선택”이라 쓰고, §헤더는 “DAQ 장비” readonly 드롭다운이라 씀. ② Notion `[C-PRJ-06] 결과 분석-파형 영역` §레이아웃·§헤더; `43_MARK_Claude-반영.md` §1. ③ 동일 UI 영역의 명칭이 달라 전달 시 다른 조작으로 읽힐 수 있음. ④ **확인 질문:** §레이아웃의 “대상 선택”이 §헤더의 “DAQ 장비”와 같은 항목인가?

## nit

6. **DAQ 다대수 전제의 문서 경계가 다름.** ① 결과 분석 헤더는 현재 `모재 1 : DAQ 1`의 readonly 표시라고 하면서도 “모재 1개에 DAQ N대 배치하는 고도화 대비 자리”를 명세 본문에 적음. 공통 지침은 다수 DAQ가 고도화 후보이고 “명세에 복수 전제를 쓰지 않음”이라고 적음. 현재 선택 동작에는 충돌이 확인되지 않으나 문서 서술 범위가 다름. ② Notion `[C-PRJ-06] 결과 분석-파형 영역` §헤더; `CLAUDE.md:114`; `43_MARK_Claude-반영.md` §1. ③ 현행 1대 구현과 미래 다대수 요구를 구분하기 어려움. ④ **확인 질문:** 이 괄호의 미래 배치 설명을 현행 화면 명세의 요구사항으로 읽어야 하는가?

## 대조 결과

- **포함 데이터:** raw·`origin/current`·수정 정보·측정값·마킹 전 필드·검사 정보의 목록은 Notion §검사 데이터 내보내기와 저장 사양 §3-2가 일치함. raw 1벌·C-scan 미저장·마킹 별도 레코드 구조와도 직접 충돌하지 않음. (`Result_Analysis_Storage_Spec_v1.0.md:16-26,93-113,135-149`)
- **저장 분기:** 교정 값 변경 때만 수정 정보 모달, 마킹만 변경 때 모달 없음, 교정+마킹 원자적 저장, 저장 실패 시 내보내기 중단은 이어 읽을 수 있음. 다만 위 2번의 부분 제외 처리는 별도 기준이 필요함. (Notion `[C-PRJ-06] 결과 분석-사이드바(교정)` §저장·초기화·삭제; `Result_Analysis_Storage_Spec_v1.0.md:157-163`)
- **3D 위치:** 결과 분석 파형 문서는 C-scan 좌상단 `2D | 3D`를 명시하고 “3D View ON”을 3D 선택 상태로 정의함. 교정·마킹 사이드바의 3D 언급은 상태 조건이며 헤더 토글 위치를 전제하지 않음. `[C-PRJ-03]`의 pane 헤더 `2D / 3D`는 별도 화면 조작이고 `[C-RPT-02]`는 헤더 `3D View` 토글을 전제하지 않음. 지정 문서에서 위치 잔여 발견 없음. (Notion 각 문서 §C-scan·§3D View·§마킹 탭·§pane 헤더·§캡처 생성)
