# 마킹 경합 규칙·문서 참조 재검토

## 발견

### S1 · should-fix · 조건부 DB 작업의 검사 범위가 적혀 있지 않음

1. **무엇이:** 마킹 번호 `M-01`부터는 **검사 단위**로 부여함. 이번에 추가한 삭제·사유 수정·시작 조건의 SQL 예시는 모두 `no = ? AND status = 'pending'`만 사용하고 검사 식별 조건을 적지 않음. 저장 형식은 검사당 `markings[]`를 JSON 또는 테이블로 허용함.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-사이드바(마킹)` §마킹 1건 항목 ‘번호’·§저장; `Result_Analysis_Storage_Spec_v1.0.md:24,100,119,123-124`.
3. **왜 문제인가:** 테이블 형태로 구현하면 다른 검사에도 같은 `no`가 존재할 수 있음. 예시 조건을 그대로 적용할 때 다른 검사의 행까지 삭제·수정·시작될 여지가 있음. JSON 형태라면 해당 SQL의 적용 범위 자체를 따로 설명해야 함.
4. **확인 질문:** 조건부 작업은 검사 ID와 마킹 번호를 함께 특정하는가? 테이블·JSON 중 실제 저장 형태가 정해지면 이 조건을 어디에 명시할 것인가?

### N1 · nit · 저장 시 팝업 뒤 지연된 상태 알림의 토스트 중복 여부가 없음 — 확인 필요

1. **무엇이:** 시작 회신이 화면에 늦게 도착하면 저장 트랜잭션에서 먼저 `0행`을 감지해 번호 팝업을 띄울 수 있음. 이후 같은 `pending → running` 알림이 화면에 도착하면 ‘저장 전 변경과 겹칠 때’의 즉시 복원·토스트 규칙도 적용되는지 적지 않음.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-사이드바(마킹)` §상태 ‘저장 전 변경과 겹칠 때’·§저장 ‘저장 전에 그 건이 이미 시작된 경우’; `Result_Analysis_Storage_Spec_v1.0.md:123-126`.
3. **왜 문제인가:** 동일한 번호에 대해 팝업과 토스트가 연달아 뜰 수 있음. 저장에서 삭제·수정 취소를 화면에도 반영한다면 이후 알림은 일반 상태 갱신만 수행해 중복이 없겠지만, 그 처리 범위가 명시되지 않음.
4. **확인 질문:** 저장 시 `0행`으로 거부한 건의 화면 변경은 그 자리에서 복원·해제하는가? 이후 같은 상태 알림이 도착하면 토스트를 다시 표시하는가?

## 확인된 반영

- 상태 변경과 삭제·사유 수정은 모두 `pending` 조건으로 같은 행에 적용됨. 먼저 확정된 작업을 우선하고, 시작이 먼저면 그 건을 제외·번호 알림 후 나머지를 저장한다는 규칙은 Notion 마킹 사이드바 §저장과 저장 사양 §3-1에서 일치함. 다만 S1의 **검사별 식별 범위**는 별도 확인 필요.
- 교정+마킹은 **허용된 변경 집합**을 한 트랜잭션으로 저장함. 이미 시작된 마킹 행을 제외하는 것은 실패가 아니며, 트랜잭션 자체가 실패하면 두 탭의 입력값과 수정 정보 입력값을 유지한다는 규칙은 Notion 교정·마킹 사이드바와 저장 사양 §4에서 일치함.
- `[C-SET-01] 프로그램 설정`의 완료 검사 목록, `[C-PRJ-05] 측정 및 교정-파형 영역`의 Gate 조작·활성 수, `-사이드바`의 DGS Gain Δ는 각각 담당 결과 분석 문서명으로 바뀜. 화면 단위 참조를 제외하면 화면설계서 DB에 남은 `[C-PRJ-06] 결과 분석` 내용 참조는 확인되지 않음.
