# 마킹 행 식별·알림 중복 재검토

## 발견

### S1 · should-fix · 저장 진행 중 상태 알림이 먼저 도착하면 팝업과 토스트가 함께 발생할 수 있음

1. **무엇이:** `0행`으로 저장에서 제외된 카드는 번호 팝업과 함께 화면 값을 복원하고, **이후** 같은 상태 알림에는 토스트를 띄우지 않도록 정함. 반대 순서, 즉 사용자가 `[저장]`을 누른 뒤 상태 알림이 **저장 응답보다 먼저** 도착하면 해당 카드에 아직 미저장 삭제·사유 수정이 있어 즉시 복원 토스트 조건을 만족함. 뒤이어 조건부 DB 작업의 `0행` 결과가 돌아오면 번호 팝업도 표시하는지 정해져 있지 않음.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-사이드바(마킹)` §상태 ‘저장 전 변경과 겹칠 때’·§저장 ‘저장 전에 그 건이 이미 시작된 경우’; `Result_Analysis_Storage_Spec_v1.0.md:124,126-128`.
3. **왜 문제인가:** 새 규칙은 **팝업 → 지연 알림** 순서의 중복을 막지만, **알림 → 저장 응답** 순서에는 동일한 건의 토스트와 팝업이 모두 열릴 수 있음. 화면에서 변경을 이미 복원한 건을 저장 결과가 다시 알리는지 구현자마다 달라짐.
4. **확인 질문:** 저장 요청 중 상태 알림을 받아 토스트·복원을 마친 번호는 이후 `0행` 저장 응답의 번호 팝업에서 제외하는가? 팝업 대상이 모두 먼저 처리됐다면 팝업을 생략하는가?

## 확인된 반영

- 마킹 번호는 검사별 연번이고, 조건부 삭제·사유 수정·시작의 행 식별은 모두 `inspection_id` + `no`로 적혀 있음. 번호 카운터는 검사 메타 레코드에 두며 삽입과 같은 트랜잭션으로 확정함. 검사 삭제는 해당 검사의 `markings[]`를 함께 삭제하는 규칙임. (`Result_Analysis_Storage_Spec_v1.0.md:24,100,119-125,129,142`)
- **저장 결과가 먼저 도착한 뒤 상태 알림이 늦게 오는 순서**에는 번호 팝업 시 카드 값을 복원하고, 뒤의 알림은 배지만 갱신한다는 Notion·저장 사양의 규칙이 일치함. (`[C-PRJ-06] 결과 분석-사이드바(마킹)` §저장; `Result_Analysis_Storage_Spec_v1.0.md:128`)
