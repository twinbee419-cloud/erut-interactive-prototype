# 마킹 구조 전환 반영 재검토

> Codex · 2026-11-10 · 대상: `33_MARK_Claude-반영.md` §4의 4항목. Notion `[C-PRJ-06]` 결과 분석 3문서를 새로 읽고 `03_dev_handoff/Result_Analysis_Storage_Spec_v1.0.md`와 대조. §5·기존 미결·자동화 장비 제어 페이지의 실행 설계는 제외. 아래는 발견과 확인 질문이며 기획 판정이 아님.

## 발견

### S1 · should-fix · 마킹만 저장한 경우의 `수정 일시`가 문서마다 다름

1. **무엇이:** 파형 영역의 검사 선택 모달은 `수정 일시`를 “마지막으로 [저장]한 시점”으로 정의함. 교정 사이드바와 저장 사양은 마킹만 바뀐 [저장]에서 `수정 일시`를 변경하지 않는다고 명시함.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-파형 영역` §검사 불러오기 ‘테이블 컬럼 4개’; `[C-PRJ-06] 결과 분석-사이드바(교정)` §저장·초기화·삭제; `Result_Analysis_Storage_Spec_v1.0.md:139`.
3. **왜 문제인가:** 마킹만 저장한 검사의 목록 시각을 구현자가 마지막 공통 저장 시각과 마지막 교정 저장 시각 중 임의로 해석할 수 있음.
4. **확인 질문:** 파형 영역의 `수정 일시` 설명은 교정 값 변경을 저장한 시각으로 한정하는가?

### S2 · should-fix · 수정 정보 모달의 표시 조건이 같은 문서 안에서 충돌

1. **무엇이:** 교정 사이드바 §저장·초기화·삭제는 “교정 값이 바뀐 경우에만” 입력 모달을 띄우고 마킹만 바뀌면 바로 저장한다고 함. 같은 문서 §수정 정보 모달은 입력 모달의 진입 조건을 조건 없이 “사이드바 [저장] 클릭 시”로 적음.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-사이드바(교정)` §저장·초기화·삭제와 §수정 정보 모달 ‘① 입력 모달’; `[C-PRJ-06] 결과 분석-사이드바(마킹)` §저장.
3. **왜 문제인가:** 마킹만 저장할 때 모달을 건너뛰는지에 대한 구현 지시가 한 문서 안에서 갈림.
4. **확인 질문:** 입력 모달의 진입 문장에도 교정 값 변경 조건을 명시할 것인가?

### S3 · should-fix · 저장 전 삭제한 마킹이 실행을 시작할 때 화면 복귀 규칙이 없음

1. **무엇이:** `대기` 마킹의 [🗑] 클릭은 저장 전에도 카드를 목록에서 즉시 제거함. 그 사이 자동화 장비 제어 페이지가 같은 DB 행을 `진행중`으로 바꾸면 상태는 결과 분석에 “즉시 반영”되어야 하지만, 카드는 이미 화면에서 사라짐. 저장 시 삭제 거부·번호 팝업은 정해졌으나 카드와 마킹 사유를 언제 어떤 값으로 복귀시키는지 없음.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-사이드바(마킹)` §목록 ‘[🗑]’·§상태·§저장 ‘저장 전에 그 건이 이미 시작된 경우’; `Result_Analysis_Storage_Spec_v1.0.md:121-124`.
3. **왜 문제인가:** 진행 상태와 실제 목록이 저장 전후에 달라지고, 거부된 삭제의 화면 복구가 구현마다 달라질 수 있음.
4. **확인 질문:** 저장 전 삭제로 숨긴 건이 `진행중`이 되면 즉시 다시 표시하는가, 저장 거부 시 복귀하는가? 복귀 시 로컬 수정 중이던 사유와 DB의 사유 중 무엇을 표시하는가?

### S4 · should-fix · 교정과 마킹을 함께 저장할 때 부분 실패 처리 범위가 없음

1. **무엇이:** 공통 [저장]은 두 탭 변경을 한 번에 처리함. 저장 사양은 마킹만 변경한 경우의 트랜잭션은 명시하지만, 교정+마킹 동시 저장이 전체 원자적 작업인지, 한쪽 기록 실패 시 다른 쪽을 되돌리는지 적지 않음. 마킹 사이드바의 “저장 실패 → 변경 유지”가 두 탭 동시 저장에도 적용되는지도 없음.
2. **어디서:** Notion `[C-PRJ-06] 결과 분석-사이드바(교정)` §우측 사이드바—헤더·§저장·초기화·삭제; `[C-PRJ-06] 결과 분석-사이드바(마킹)` §저장; `Result_Analysis_Storage_Spec_v1.0.md:118-123,135,139-140`.
3. **왜 문제인가:** 교정 설정만 저장되고 마킹은 저장되지 않는 등 화면이 한 번의 저장으로 약속한 상태와 DB가 달라질 수 있음.
4. **확인 질문:** 교정+마킹 저장은 하나의 트랜잭션으로 모두 성공하거나 모두 취소하는가? 실패 시 두 탭의 입력값·수정 정보 모달·오류 안내는 어떻게 유지하는가?

### S5 · should-fix · 분할 후 다른 화면의 `[C-PRJ-06] 결과 분석` 참조 대상이 유일하지 않음

1. **무엇이:** Notion DB의 현재 문서명은 `-파형 영역`·`-사이드바(교정)`·`-사이드바(마킹)` 3개이며, 정확히 `[C-PRJ-06] 결과 분석`이라는 문서는 없음. 다른 화면은 여전히 분할 전 이름으로 참조함. 특히 측정값·필터·캡처 출처는 파형 영역, 사후 조정은 교정 사이드바 설명과 연결되나 해당 문서명이 참조에 없음.
2. **어디서:** Notion `[C-PRJ-03] 종합 결과` §측정값·§참고; `[C-RPT-02] 스캔 보고서` §캡처 생성; `[C-PRJ-02] 대시보드` §참고; `[C-SET-06] 스캔 계획` §오버랩; `[공통] 메뉴바/상태바` §측정 메뉴. 분할된 3문서의 문서명은 Notion 화면설계서 DB.
3. **왜 문제인가:** 화면 이동을 뜻하는 ID 표기라면 동작 가능하지만, 명세 문서 참조라면 검토자와 구현자가 어느 페이지를 읽어야 할지 바로 알 수 없음.
4. **확인 질문:** 이 참조들을 화면 이동용 약칭으로 둘 것인가, 명세 참조에는 담당 문서의 전체 이름을 붙일 것인가? 특히 PRJ-03의 측정값·필터와 RPT-02의 캡처 출처가 가리킬 문서를 확인해 달라.

### N1 · nit · 저장 사양의 상태 기록 작성자 설명이 `failReason`을 빠뜨림

1. **무엇이:** §3-1 도입부는 자동화 장비 제어 페이지가 `status`만 쓴다고 함. 같은 절의 상태 반영 규칙과 §4 트리거 표는 `status`와 `failReason`을 함께 갱신한다고 적음.
2. **어디서:** `Result_Analysis_Storage_Spec_v1.0.md:95-96,110-111,124,141`.
3. **왜 문제인가:** 실패 사유의 작성 책임이 첫 문장과 상세 규칙에서 달라 보임.
4. **확인 질문:** §3-1의 “`status`만”을 `status`·`failReason`으로 명확히 할 것인가?

## 확인된 일치

- 교정만 바뀌면 수정 정보 모달·수정 일시 갱신, 마킹만 바뀌면 둘 다 생략, 두 탭이 바뀌면 함께 저장한다는 핵심 분기는 교정·마킹 사이드바와 저장 사양 §4에서 일치함. 다만 S1·S2의 주변 문장이 이 분기와 어긋남.
- `[↻]`는 교정 값만 초기화하고 저장 전에는 화면 상태만 바꾸며, `진행중` 마킹이 있으면 검사 전체 삭제를 막는 규칙은 교정 사이드바와 저장 사양 §3-1·§4에서 일치함.
- 결과 분석 3문서와 저장 사양 §3-1에는 **실행 대상 선택** 체크박스·`[마킹 실행]`·`결과 미확인`·`[표시 확인됨]`·재시작 복구·마킹 즉시 저장 규칙이 남아 있지 않음. 실행 쪽 설계는 이번 검토 범위 밖임.
